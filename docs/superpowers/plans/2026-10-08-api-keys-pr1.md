# Personal API keys, backend (PR 1 of 2) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Keys that sign scripts in with `Authorization: Bearer fb_live_…`, narrowed to read-only or read-write, some spaces or all, with or without private notes, rate-limited, and managed through `/api/api-keys`.

**Architecture:**
- **App:** a new `api_keys` app holds the model, the services (make, revoke, sign in), the Ninja `ApiKeyAuth` (an `HttpBearer`) and the key-management router.
- **Signing in:** the API's default auth becomes `[ApiKeyAuth(), django_auth]`. A key puts its `Access.limited(...)` on the request, and `core.api.access_for` returns it, so `access/policy.py` decides everything as it already does.
- **Login cookie only:** the account-level routers declare `auth=django_auth`, and a route test keeps every endpoint on one side on purpose.

**Tech Stack:** Django 6.1 + Django Ninja (`ninja.security.HttpBearer`, `django_auth`), PostgreSQL, pytest.

**Spec:** `docs/superpowers/specs/2026-10-08-api-keys-design.md` (§1–4, Errors and edge cases, Tests; §5 is PR 2).

## Global Constraints

- **The key:** `fb_live_` followed by 32 characters from letters and digits (`secrets.choice`).
  - Stored: SHA-256 hex of the whole key (`hashed`, unique) and `last_five`.
  - The full key is returned only by `POST /api/api-keys`, never again.
- **A key that fails to sign in:** unknown, expired (`expires_at <= now`), or owner `is_active=False` gives **401** `{"detail": "This API key isn't valid."}`.
  - It must be **raised** from `authenticate`, never `None`. Returning `None` would let Ninja fall through to the login cookie.
- **Rate limit:** 120 requests per key per 60-second window.
  - Over it: **429** `{"detail": "Too many requests for this API key. Try again in a minute."}`, with `Retry-After` set to the whole seconds left in the window, at least 1.
  - Every signed-in request sets `last_used_at`.
- **Login cookie only** (`auth=django_auth`):
  - everything under `/api/auth` except `GET /api/auth/me`, which takes keys;
  - `/api/setup`, `/api/users`, `/api/invites`, `/api/api-keys`;
  - `POST /api/export/restore/check`, `POST /api/export/restore`.

  Endpoints that are already `auth=None` stay public.
- **What a key can do** is decided only by `policy.py` through `access_for`. There are no key checks inside views.
- **Expiry choices:** `"30d"` (30 days), `"90d"` (90 days, the default), `"1y"` (365 days), `"never"` (`expires_at = None`).
- **Copy:**
  - name errors: 422 on `name`;
  - a space you can't see, or that doesn't exist: 422 `{"space_ids": "That space isn't one you can pick."}`;
  - empty `space_ids: []`: 422 `{"space_ids": "Pick at least one space, or All spaces."}`.
- **AGENTS.md:** 404 for what you can't see, `{"items", "count"}` lists of 50 with constant query counts, Conventional Commits with no attribution, `npm run api:generate` after API changes.

## Review Focus

- **A bad key together with a login cookie** (a developer trying the API in a logged-in browser tab): 401, never the cookie's full access (Task 2 `test_a_bad_key_never_falls_back_to_the_login_cookie`).
- **A key limited to spaces that were all deleted since:** it sees no people, and is never widened to all spaces (Task 2 `test_a_key_whose_spaces_are_gone_sees_nothing`).
- **The owner leaves a space the key was limited to:** the key no longer sees it (Task 4 `test_leaving_a_space_takes_it_from_the_key`).
- **The rate limit is per key:** a second key of the same user still works while the first is limited (Task 3 `test_the_limit_is_per_key`).
- **The full key never comes back:** the list and the stored row hold neither the key nor anything that gives it back (Task 1 `test_the_key_is_shown_once`).

### Task 3: Rate limit and "last used"

**Files:**
- Modify:
  - `backend/api_keys/services.py`: `RATE_LIMIT = 120`, `WINDOW = timedelta(minutes=1)`, `count_request(key, now=None) -> None` raising `TooManyRequests(retry_after: int)`;
  - `backend/api_keys/auth.py`: call it after the key is found;
  - `backend/config/api.py`: the 429 handler sets `Retry-After`.
- Test: `backend/tests/api_keys/test_rate_limit.py`

**Interfaces:**
- Produces: `class TooManyRequests(Exception): retry_after: int`; `count_request(key: ApiKey, now: datetime | None = None) -> None`.
- `count_request` uses at most two atomic `UPDATE`s, with no raw SQL and no cache:
  1. Start a new window where the old one is over: `filter(pk, Q(window_start__isnull=True) | Q(window_start__lte=now - WINDOW)).update(window_start=now, window_count=1, last_used_at=now)`.
  2. If that changed no row, add one within the window: `filter(pk, window_count__lt=RATE_LIMIT).update(window_count=F("window_count") + 1, last_used_at=now)`.
  3. If neither changed a row, raise `TooManyRequests(retry_after=max(1, ceil((key.window_start + WINDOW - now).total_seconds())))`.

  (This replaces the spec's "one UPDATE … RETURNING", which needs raw SQL; AGENTS.md keeps raw SQL to graph queries. Two statements still stay exact across processes.)

  - `test_a_new_minute_starts_again`: `window_start` 61 seconds back with count 120 → 200, and the count is now 1.
